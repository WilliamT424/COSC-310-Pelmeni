# COSC-310-Pelmeni

## Team name: 
  Pelmeni

A food-delivery backend (FastAPI) with a small browser frontend. Milestone 1 covers the **Restaurant component**: customers can browse, search and view restaurants and their menus, and restaurant data can be created and updated.

## Requirements:
- Python 3.12

## Setup:
Clone the repository: https://github.com/WilliamT424/COSC-310-Pelmeni.git

```bash
git clone https://github.com/WilliamT424/COSC-310-Pelmeni.git
cd COSC-310-Pelmeni
```

## Virtual Environment

Create a virtual environment:

```bash
python -m venv .venv
```

Activate the virtual environment:
- Windows:
```bash
.venv\Scripts\Activate.ps1
```
- macOS/Linux:
```bash
source .venv/bin/activate
```

## Dependency Installation

Install the required dependencies:

```bash
pip install -r requirements.txt
```

## Starting the Application

Start the FastAPI application with:

```bash
python -m uvicorn app.main:app --reload
```

Then open:

| URL | What it is |
| --- | --- |
| http://127.0.0.1:8000/ui/ | The basic frontend (restaurant list, search, details, menus, create/edit forms) |
| http://127.0.0.1:8000/docs | Interactive OpenAPI documentation generated by FastAPI |

The frontend talks to the REST API on the same origin; no restaurant data is hard-coded in it.

## Scope (Milestone 1)

**In scope** — customer-facing: list restaurants, search/filter, restaurant details, view menus, view menu items. Restaurant management: create a restaurant, update a restaurant, add a menu item, update a menu item.

**Out of scope** — customer registration, authentication, authorization, shopping carts, checkout, orders and deliveries.

The vertical slice we demonstrate is:

```text
Restaurant List → Search / Filter → Restaurant Details → Menu → Menu Items
```

## API Contract

Base URL: `http://127.0.0.1:8000`. All request and response bodies are JSON. Errors use FastAPI's standard shape, `{"detail": "..."}` (a list of validation errors for 422).

### Models

**Restaurant**

| Field | Type | Rules |
| --- | --- | --- |
| `id` | int | Assigned by the server (next id after the current highest); never sent by the client |
| `name` | string | Non-empty |
| `rating` | float | 0–5 |
| `cuisine` | string | Non-empty |
| `deliveryTime` | int | Minutes, ≥ 0 |

**Menu** — `id` (int), `restaurant_id` (int), `name` (string), `items` (list of Menu Item)

**Menu Item** — `id` (int, assigned by the server within its menu), `name` (non-empty string), `description` (string, default `""`), `price` (float, ≥ 0), `available` (bool, default `true`)

### Endpoints

| Method | Path | Description | Success | Errors |
| --- | --- | --- | --- | --- |
| GET | `/` | Welcome message | 200 | |
| GET | `/health` | Health check, returns `{"status": "healthy"}` | 200 | |
| GET | `/restaurants` | All restaurants, as `{"restaurants": [Restaurant]}` | 200 | |
| GET | `/restaurants/search` | Restaurants matching **all** provided filters (see below); no filters returns everything; no match returns `{"restaurants": []}` | 200 | 422 invalid filter |
| GET | `/restaurants/{restaurant_id}` | Details of one restaurant | 200 | 404 restaurant not found |
| GET | `/restaurants/{restaurant_id}/menus` | The restaurant's menus, each with its items (`[]` if it has none) | 200 | 404 restaurant not found |
| GET | `/restaurants/{restaurant_id}/menus/{menu_id}/items` | Items of one menu | 200 | 404 menu not found |
| GET | `/restaurants/{restaurant_id}/menus/{menu_id}/items/{item_id}` | One menu item | 200 | 404 menu or item not found |
| POST | `/restaurants` | Create a restaurant. Body: `name`, `rating`, `cuisine`, `deliveryTime` (an `id` in the body is ignored) | 201 + Restaurant | 422 invalid or missing field |
| PATCH | `/restaurants/{restaurant_id}` | Update only the provided fields. Body: any of `name`, `rating`, `cuisine`, `deliveryTime`; the id cannot be changed and a provided field cannot be `null` | 200 + Restaurant | 404 not found, 422 invalid value |
| POST | `/restaurants/{restaurant_id}/menus/{menu_id}/items` | Add a menu item. Body: `name`, `price`, optional `description`, `available` | 201 + Menu Item | 404 menu not found, 422 invalid item |
| PATCH | `/restaurants/{restaurant_id}/menus/{menu_id}/items/{item_id}` | Update only the provided fields of a menu item | 200 + Menu Item | 404 menu or item not found, 422 invalid value |

**Search filters** (query parameters on `GET /restaurants/search`, all optional):

| Parameter | Type | Meaning |
| --- | --- | --- |
| `name` | string | Case-insensitive substring of the restaurant name |
| `cuisine` | string | Case-insensitive substring of the cuisine |
| `min_rating` | float, 0–5 | Rating must be at least this |
| `max_delivery_time` | int, ≥ 0 | Delivery time must be at most this many minutes |

Example:

```bash
curl "http://127.0.0.1:8000/restaurants/search?cuisine=japanese&max_delivery_time=30"
curl -X POST http://127.0.0.1:8000/restaurants -H "Content-Type: application/json" \
     -d '{"name": "Beta", "rating": 4.5, "cuisine": "Chinese", "deliveryTime": 30}'
```

## Architecture

Every request follows `route → service → repository → JSON file`:

| Layer | Location | Responsibility |
| --- | --- | --- |
| Routes | `app/main.py` | HTTP only: parameters, status codes, translating "not found" into 404 |
| Services | `app/services/` | Business logic (search, id assignment, menu item rules). No FastAPI imports; "not found" is returned as `None` |
| Repositories | `app/repositories/` | Reading and writing the JSON files |
| Schemas | `app/schemas/` | Pydantic models for request and response data |

### Design decisions

- **Server-assigned ids.** Restaurants and menu items get their id from the server, and a client-sent id is ignored. This keeps ids unique and stable, removes the duplicate-id failure case, and means the frontend no longer has to guess a free id.
- **Separate create, update and stored models.** `RestaurantCreate` has no `id`; `RestaurantUpdate` makes every field optional but rejects an explicit `null`, so a partial update can never write invalid data into `restaurants.json`. The same constraints (rating 0–5, non-negative delivery time and price, non-empty names) apply everywhere.
- **Atomic JSON writes.** Both repositories save through `app/repositories/json_storage.py`, which writes a temporary file and then replaces the data file in one step. A crash mid-write can't leave a half-written `restaurants.json` or `menus.json`.
- **Menus stored separately, linked by `restaurant_id`.** Menus live in `data/menus.json` so restaurant and menu data can change independently. A restaurant with no menus returns `[]`; 404 means the restaurant itself doesn't exist.
- **Testable file paths.** Repository file locations are resolved when called, so tests point them at temporary copies. A session-wide test fixture fails the run if any test modifies the committed files in `data/`.

## Representative Data

Data is persisted as JSON and survives restarts:

```text
data/restaurants.json   # restaurants
data/menus.json         # menus and menu items, linked by restaurant_id
```

## Running tests

Run the test suite with pytest:

```bash
pytest
```

The suite covers the health endpoint, restaurant list/search/details, menus and menu items, create/update (including invalid input and not-found cases), repository behaviour, persistence across restarts, and the frontend being served. GitHub Actions (`.github/workflows/python-app.yml`) runs flake8 and pytest on pushes and pull requests to `main`.
