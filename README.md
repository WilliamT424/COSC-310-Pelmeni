# COSC-310-Pelmeni

## Team name: 
  Pelmeni

A food-delivery application with a FastAPI backend and a small browser frontend. The current implementation supports restaurant discovery and management, plus customer account registration, profile updates, and deactivation.

## Requirements:
- Python 3.12

## Setup:
Clone the repository: https://github.com/WilliamT424/COSC-310-Pelmeni.git

```bash
git clone https://github.com/WilliamT424/COSC-310-Pelmeni.git
cd COSC-310-Pelmeni
```

## Virtual Environment

Create a virtual environment:

```bash
python -m venv .venv
```

Activate the virtual environment:
- Windows:
```bash
.venv\Scripts\Activate.ps1
```
- macOS/Linux:
```bash
source .venv/bin/activate
```

## Dependency Installation

Install the required dependencies:

```bash
pip install -r requirements.txt
```

## Starting the Application

Start the FastAPI application with:

```bash
python -m uvicorn app.main:app --reload
```

Then open:

| URL | What it is |
| --- | --- |
| http://127.0.0.1:8000/ui/ | The frontend for restaurant browsing and management, plus customer signup and profile management |
| http://127.0.0.1:8000/docs | Interactive OpenAPI documentation generated by FastAPI |

The frontend talks to the REST API on the same origin; restaurant and customer records are loaded from the backend.

## Current Scope

**Restaurant features:** list, search and filter restaurants; view restaurant details, menus and menu items; create and update restaurants; add and update menu items.

**Customer account features:** register, retrieve and update a customer profile, and deactivate an account. Authentication and authorization are not implemented. Shopping carts, checkout, orders and deliveries are also outside the current implementation.

The restaurant browsing flow is:

```text
Restaurant List -> Search / Filter -> Restaurant Details -> Menu -> Menu Items
```
## API Contract

Base URL: `http://127.0.0.1:8000`. All request and response bodies are JSON. Errors use FastAPI's standard shape, `{"detail": "..."}` (a list of validation errors for 422).

### Models

**Restaurant**

| Field | Type | Rules |
| --- | --- | --- |
| `id` | int | Assigned by the server (next id after the current highest); never sent by the client |
| `name` | string | Non-empty |
| `rating` | float | 0–5 |
| `cuisine` | string | Non-empty |
| `deliveryTime` | int | Minutes, ≥ 0 |

**Menu** — `id` (int), `restaurant_id` (int), `name` (string), `items` (list of Menu Item)

**Menu Item** — `id` (int, assigned by the server within its menu), `name` (non-empty string), `description` (string, default `""`), `price` (float, ≥ 0), `available` (bool, default `true`)

**Customer** (response)

| Field | Type | Rules |
| --- | --- | --- |
| `customerId` | int | Assigned by the server |
| `name` | string | Non-empty |
| `email` | string | Non-empty; unique across customer accounts |
| `deliveryAddress` | `Address` | Required nested delivery address |
| `status` | bool | `true` for an active account; `false` after deactivation |

**Address** — `street`, `city`, `province`, `postal_code`, and `country` are required non-empty strings.

**CustomerCreate** (request) — `name`, `email`, `street`, `city`, `province`, `postal_code`, and `country`. Address fields are submitted at the top level. The server assigns `customerId` and initializes `status` to `true`.

**CustomerUpdate** (request) — any subset of `name`, `email`, `street`, `city`, `province`, `postal_code`, and `country`. Address fields remain top-level; omitted fields are unchanged. The response is a complete `Customer` object.

### Endpoints

| Method | Path | Description | Success | Errors |
| --- | --- | --- | --- | --- |
| GET | `/` | Welcome message | 200 | |
| GET | `/health` | Health check, returns `{"status": "healthy"}` | 200 | |
| GET | `/restaurants` | All restaurants, as `{"restaurants": [Restaurant]}` | 200 | |
| GET | `/restaurants/search` | Restaurants matching **all** provided filters (see below); no filters returns everything; no match returns `{"restaurants": []}` | 200 | 422 invalid filter |
| GET | `/restaurants/{restaurant_id}` | Details of one restaurant | 200 | 404 restaurant not found |
| GET | `/restaurants/{restaurant_id}/menus` | The restaurant's menus, each with its items (`[]` if it has none) | 200 | 404 restaurant not found |
| GET | `/restaurants/{restaurant_id}/menus/{menu_id}/items` | Items of one menu | 200 | 404 menu not found |
| GET | `/restaurants/{restaurant_id}/menus/{menu_id}/items/{item_id}` | One menu item | 200 | 404 menu or item not found |
| POST | `/restaurants` | Create a restaurant. Body: `name`, `rating`, `cuisine`, `deliveryTime` (an `id` in the body is ignored) | 201 + Restaurant | 422 invalid or missing field |
| PATCH | `/restaurants/{restaurant_id}` | Update only the provided fields. Body: any of `name`, `rating`, `cuisine`, `deliveryTime`; the id cannot be changed and a provided field cannot be `null` | 200 + Restaurant | 404 not found, 422 invalid value |
| POST | `/restaurants/{restaurant_id}/menus/{menu_id}/items` | Add a menu item. Body: `name`, `price`, optional `description`, `available` | 201 + Menu Item | 404 menu not found, 422 invalid item |
| PATCH | `/restaurants/{restaurant_id}/menus/{menu_id}/items/{item_id}` | Update only the provided fields of a menu item | 200 + Menu Item | 404 menu or item not found, 422 invalid value |

### Customer Account Endpoints

These routes manage customer profiles. `customer_id` is the integer `customerId` assigned during registration. Authentication and authorization are not implemented; the customer ID is not a login credential.

| Method | Path | Parameters and request body | Success response | Errors |
| --- | --- | --- | --- | --- |
| POST | `/customers` | JSON `CustomerCreate`; required fields: `name`, `email`, `street`, `city`, `province`, `postal_code`, `country` | 201 + `Customer` | 409 email already registered; 422 missing, empty, or invalid field |
| GET | `/customers/{customer_id}` | Path: `customer_id` (integer customer ID) | 200 + `Customer` | 404 customer not found; 422 customer ID is not an integer |
| PATCH | `/customers/{customer_id}` | Path: `customer_id`; JSON `CustomerUpdate` with one or more supported fields | 200 + updated `Customer` | 404 customer not found; 422 invalid ID or body field |
| POST | `/customers/{customer_id}/deactivate` | Path: `customer_id`; no request body | 200 + deactivated `Customer` (`status: false`) | 404 customer not found; 422 customer ID is not an integer |

Registration request example:

```json
{
  "name": "Test Customer",
  "email": "test@example.com",
  "street": "123 Test Street",
  "city": "Kelowna",
  "province": "BC",
  "postal_code": "V1Y 1A1",
  "country": "Canada"
}
```

Customer response example:

```json
{
  "customerId": 6,
  "name": "Test Customer",
  "email": "test@example.com",
  "deliveryAddress": {
    "street": "123 Test Street",
    "city": "Kelowna",
    "province": "BC",
    "postal_code": "V1Y 1A1",
    "country": "Canada"
  },
  "status": true
}
```

Update example (only the supplied field changes):

```json
{"city": "Vancouver"}
```

Representative error responses:

```json
{"detail": "Customer not found"}
```

```json
{"detail": "Please update your existing account instead of creating a new one."}
```

Validation failures use HTTP 422 and FastAPI's standard `detail` array, for example a missing required field:

```json
{"detail": [{"loc": ["body", "email"], "msg": "Field required", "type": "missing"}]}
```

The browser frontend provides customer registration and profile editing. After registration, the **Customers** header link opens that customer's profile; the profile page can deactivate the account or log out of the local profile view. This is a frontend convenience, not authentication.

**Search filters** (query parameters on `GET /restaurants/search`, all optional):

| Parameter | Type | Meaning |
| --- | --- | --- |
| `name` | string | Case-insensitive substring of the restaurant name |
| `cuisine` | string | Case-insensitive substring of the cuisine |
| `min_rating` | float, 0–5 | Rating must be at least this |
| `max_delivery_time` | int, ≥ 0 | Delivery time must be at most this many minutes |

Example:

```bash
curl "http://127.0.0.1:8000/restaurants/search?cuisine=japanese&max_delivery_time=30"
curl -X POST http://127.0.0.1:8000/restaurants -H "Content-Type: application/json" \
     -d '{"name": "Beta", "rating": 4.5, "cuisine": "Chinese", "deliveryTime": 30}'
```

## Architecture

Every request follows `route → service → repository → JSON file`:

| Layer | Location | Responsibility |
| --- | --- | --- |
| Routes | `app/main.py` | HTTP only: parameters, status codes, translating "not found" into 404 |
| Services | `app/services/` | Business logic (search, id assignment, menu item rules, customer account operations). No FastAPI imports; "not found" is returned as `None` |
| Repositories | `app/repositories/` | Reading and writing restaurant, menu, and customer JSON files |
| Schemas | `app/schemas/` | Pydantic models for request and response data |

### Design decisions

- **Server-assigned ids.** Restaurants, menu items, and customers get their id from the server. This keeps ids unique and stable and means the frontend does not choose ids.
- **Customer account lifecycle.** Customer records remain in `customers.json` when deactivated; deactivation changes `status` to `false` rather than deleting profile history.
- **Separate create, update and stored models.** `RestaurantCreate` has no `id`; `RestaurantUpdate` makes every field optional but rejects an explicit `null`. Menu item schemas enforce non-negative prices, while customer create and update schemas define the supported profile fields. Customer account updates are partial: omitted values remain unchanged.
- **Atomic JSON writes.** Repositories save through `app/repositories/json_storage.py`, which writes a temporary file and then replaces the data file in one step. A crash mid-write can't leave a half-written data file.
- **Menus stored separately, linked by `restaurant_id`.** Menus live in `data/menus.json` so restaurant and menu data can change independently. A restaurant with no menus returns `[]`; 404 means the restaurant itself doesn't exist.
- **Testable file paths.** Repository file locations are resolved when called, so tests point them at temporary copies. A session-wide test fixture fails the run if any test modifies the committed files in `data/`.

## Representative Data

Data is persisted as JSON and survives restarts:

## Running tests

Run the test suite with pytest:

```bash
pytest
```

The suite covers the health endpoint, restaurant list/search/details, menus and menu items, customer account operations (registration, retrieval, updates, and deactivation), invalid input and not-found cases, repository behaviour, persistence across restarts, and the frontend being served. Customer account tests exercise the service and repository layers. GitHub Actions (`.github/workflows/python-app.yml`) runs flake8 and pytest on pushes and pull requests to `main`.
